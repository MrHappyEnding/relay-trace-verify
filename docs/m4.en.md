# M4: local Kubernetes multi-worker acceptance

[![中文](assets/lang-zh.svg)](m4.md) [![English](assets/lang-en.svg)](m4.en.md)

**Status: M4 phase one—the model-free execution foundation. M4 as a whole is not complete.**
M2/M3 execution identity, checkpoints, accounting and isolated verification now run inside Kubernetes
Jobs. This phase tests two control workers and two execution nodes. Formal benchmarks and real-model
paired experiments remain outstanding.

## Lifecycle and guarantees

- Host control workers use Temporal for idempotent reconciliation; PostgreSQL persists executions and
  resource reservations. Each Execution has one Job with a private Docker daemon and Harbor sandbox.
  No host Docker socket is mounted. Kubernetes owns Pod lifecycle; RTV owns create/adopt/delete intent.
- The default pool allows two Jobs, each requesting/limiting 1 CPU and 1536 MiB. Namespace quota also
  includes PostgreSQL. Worker restart adopts existing Jobs. Node loss creates a new epoch/workspace
  only from a validated committed checkpoint, preserving Attempt and absolute TTL.
- Old epochs cannot publish. Interrupted operations remain UNKNOWN. A lease expiring does not release
  capacity: both Job and Pods must be observed absent. `rtv3` and `rtv4` have separate schemas, queues
  and runtime roots.

See [ADR 0005](adr/0005-kubernetes-executions.en.md) for design, attribution and limitations.

## Deployment

The verified target is macOS ARM64, Docker Desktop 28.5.1, k3d 5.8.3 / k3s 1.31.5, Python 3.13 on the
host and Python 3.12 in Jobs. The Kubernetes client is pinned to 31.0.0. Install `docker`, Compose,
`k3d`, `kubectl` and `uv`, and start Docker Desktop. A fresh machine downloads dependencies/images.

```bash
uv sync --locked --group runtime --python 3.13
.venv/bin/python -m rtv runtime prepare --adapter fixture
.venv/bin/python scripts/setup_temporal.py
.venv/bin/python scripts/m4_local_setup.py --build
```

The Harbor egress sidecar must also be cached; on a fresh machine first run the model-free container
probe from the [M0 guide](m0.en.md). Setup exports that sidecar and the fixture image, failing if either
is missing instead of substituting an image.

Setup creates only `rtv-m4` (one server, two agents), saving `work/m4-control/config.json` and
`work/m4-control/kubeconfig` with mode 600. It does not change the default kube context. Artifacts use
`work/m4-data`. Existing clusters with incompatible mounts are rejected. Images are pinned by digest
and checked on every node; the config freezes the archive SHA256. Use a new runtime root after changing
images/configuration.

Run these in separate terminals; do not start a second Temporal server if one is already running:

```bash
kubectl --kubeconfig work/m4-control/kubeconfig --context k3d-rtv-m4 \
  -n rtv-m4 port-forward --address=127.0.0.1 service/rtv-postgres 55434:5432
```

```bash
work/tools/temporal server start-dev --db-filename work/runtime-temporal.db \
  --ip 127.0.0.1 --port 7233 --ui-port 8233
```

Run the zero-model acceptance with a new output directory:

```bash
.venv/bin/python scripts/m4_acceptance.py \
  --config work/m4-control/config.json --output work/m4-data/acceptance-new
```

The script starts two control workers, tests duplicate submission/cancellation/TTL/worker SIGKILL,
then SIGKILLs **one execution-node container in this dedicated cluster**. It restores a checkpoint on
the other node and restarts the stopped node in finally. Keep unrelated workloads out of this cluster.

For manual use:

```bash
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual init
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual worker
# Another terminal:
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual submit --key sample --staged
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual pool
```

Use `status / cancel / events / history / ledger <trial_id>` and `report --output work/m4-report-new`.
All commands must use the same root. After draining tasks, `k3d cluster stop rtv-m4` pauses the cluster;
`k3d cluster start rtv-m4` resumes it. Restart the PostgreSQL port-forward afterwards. Stopping preserves
data and is not deletion.

## Evidence and metrics

**27 local acceptance checks pass across 7 Trials**, alongside **114 runtime unit tests (1 skipped)**,
**77 Python 3.11 core tests (38 optional-dependency skips)** and **48 [M3 regression checks](evidence/m4-m3-regression-arm64-20261011.json)**.
Checks are recorded in the [M4 evidence](evidence/m4-runtime-arm64-20261011.json). Every fault uses a deterministic
Python fixture: these are real-service/container checks, **not model-effectiveness experiments**.

Final raw artifacts are in `work/m4-data/acceptance-final/`. The single node fault takes about 29.8 seconds
to workspace restoration, including about 4.13 seconds from recovery epoch creation to claim. With n=1,
this is not a performance conclusion. Cancellation, TTL and node loss leave three UNKNOWN scripted
operations. Early image-import and image-identity failures and their fixes are retained in the evidence.

The run directory contains:

- `frozen-plan.json`: predefined cases, task specification, images/config and zero API budget.
- `acceptance.json`: checks, versions, duration, faults and evidence digest.
- `faults.json`, `capacity-samples.json`: actual injection timestamps and admission samples.
- `final-report/{report.json,summary.csv,trials/*.json}`: all outcomes, events, ledger, executions and SHA256.
- `snapshot-with-incomplete/`: deliberately includes a sealed trial to test incomplete-sample retention.
- `temporal-history.json`: replayable control history; each Execution retains supervisor logs, result and
  restored workspace.

`queue_seconds` runs from submission to first claim. `elapsed_seconds` ends at the current epoch's
terminal event, excluding later cleanup. `recovery_to_claim_seconds` begins at recovery epoch creation,
**not** fault injection. `faults.json` separately records injection-to-workspace-restoration time.
p50/p95 include sample count; a single recovery is not a performance benchmark or SLO. UNKNOWN here
means an interrupted scripted operation, with no model bill, not proof of real API billing accuracy.

## Cost, limitations and remaining work

This phase makes zero paid API calls and provisions no cloud resources. It uses existing local CPU,
RAM and disk; the four lab H100s are unused. The prior $8 approval belonged to M3. M4 paid runs need a
separate concrete budget.

All Kubernetes nodes share one physical host. Local storage, PostgreSQL and Temporal are not HA;
host power loss and multi-machine storage have not been tested. The privileged outer Pod is for trusted
development only. No general exactly-once external-effect or relay-advantage claim is made.

Task selection, exclusions, repeats, execution caps and statistics are now frozen in the
[benchmark protocol](m4-benchmark.en.md), with offline verifier controls passing for one development
task. These do not extend the Kubernetes fixture acceptance scope. API reservations still require
current-price validation and approval. [Local repository integration](m4-repositories.en.md) now passes
scripted recovery acceptance. Repository resources, platform, task delivery and observation linkage are
covered in [Kubernetes repository integration](m4-repository-cluster.en.md). The [credential path and pilot launcher](m4-model-pilot.en.md) pass fake-credential checks.
Real session acceptance, other pilot environments, paid paired experiments and the full
demonstration/report remain pending. The existing M3 local dual-agent entry point remains available.
