## 生命周期与保证

- 控制 worker 在宿主运行，通过 Temporal 驱动幂等协调；PostgreSQL 保存执行与资源预约。
- 一个 Execution 对应一个 Job；每个 Job 有自己的 Docker daemon 和 Harbor 沙箱。
  Job 不挂宿主 Docker socket。Kubernetes 管理 Pod 生命周期，RTV 控制创建、接管和删除意图。
- 默认资源池最多 2 个 Job，每个 1 CPU / 1536 MiB；namespace 配额还包含 PostgreSQL。
- worker 重启查询原 Job；节点失联后，只从已提交 checkpoint 创建新的 epoch 和工作区。
  原始 TTL 保留，旧 epoch 被拒绝发布，未决调用保留 UNKNOWN。
- 旧节点的 Job/Pod 尚未确认删除时，预约继续占用配额；不会因为租约超时就假定物理资源消失。
- `rtv3` / `rtv4` 分 schema、队列、运行目录；不会把 M3 历史当成 M4 结果。

设计、参考归属与取舍见 [ADR 0005](adr/0005-kubernetes-executions.md)。

## 部署

已验收目标是 macOS ARM64 + Docker Desktop 28.5.1、k3d 5.8.3 / k3s 1.31.5，Python 3.13
运行控制面，Job 内 Python 3.12。Kubernetes Python client 固定 31.0.0。需要 `docker`、
Compose、`k3d`、`kubectl`、`uv`；Docker Desktop 需已启动。新机器需要下载依赖及镜像。

```bash
uv sync --locked --group runtime --python 3.13
.venv/bin/python -m rtv runtime prepare --adapter fixture
.venv/bin/python scripts/setup_temporal.py
.venv/bin/python scripts/m4_local_setup.py --build
```

`runtime prepare` 必须已有 Harbor egress sidecar 镜像；如果未缓存，先按 [M0 指南](m0.md)
完成一次零模型容器预检查。setup 会导出 fixture 和该 sidecar，任一缺失则报错，不静默换镜像。

setup 只使用独立集群 `rtv-m4`，创建 1 server + 2 agents。配置写入
`work/m4-control/config.json`，kubeconfig 为 `work/m4-control/kubeconfig`，权限 600。
不切换默认 kube context。产物映射在 `work/m4-data`；已有集群挂载不匹配时拒绝复用。
镜像使用 digest，并核对每个节点实际持有的身份；配置包含归档 SHA256。
重建镜像后必须用新的运行根目录，不能改变已有资源池的冻结配置。

分别在两个终端启动（若 Temporal 已运行，不重复启动）：

```bash
kubectl --kubeconfig work/m4-control/kubeconfig --context k3d-rtv-m4 \
  -n rtv-m4 port-forward --address=127.0.0.1 service/rtv-postgres 55434:5432
```

```bash
work/tools/temporal server start-dev --db-filename work/runtime-temporal.db \
  --ip 127.0.0.1 --port 7233 --ui-port 8233
```

运行可复现的零费用故障验收，输出目录必须不存在：

```bash
.venv/bin/python scripts/m4_acceptance.py \
  --config work/m4-control/config.json --output work/m4-data/acceptance-new
```

脚本启动两个控制 worker，重复提交、取消、触发 TTL、杀死 worker，随后 SIGKILL **该测试集群的
一个执行节点容器**，从 checkpoint 在另一节点恢复，并在 finally 中重新启动被停止的节点。
它不触碰其他集群。不要在这个专用测试集群混放其他任务。

手动操作可用：

```bash
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual init
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual worker
# 另一个终端：
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual submit --key sample --staged
.venv/bin/python -m rtv cluster --config work/m4-control/config.json --root work/m4-data/manual pool
```

`status / cancel / events / history / ledger <trial_id>` 查询或取消；
`report --output work/m4-report-new` 导出新快照。初始化/提交/worker 使用同一个 root。
完成所有任务后可 `k3d cluster stop rtv-m4` 暂停集群，`k3d cluster start rtv-m4`
恢复；重新启动 PostgreSQL port-forward。停止集群保留数据，不等同于删除。

## 证据与报告口径

本机验收 **27 项检查通过，包含 7 个 Trial**；runtime 单元测试 **114 通过 / 1 跳过**，
Python 3.11 core **77 通过 / 38 跳过可选依赖测试**；[M3 回归](evidence/m4-m3-regression-arm64-20261011.json)
**48 项通过**。完整检查项见 [M4 证据](evidence/m4-runtime-arm64-20261011.json)。
所有故障都使用确定性 Python fixture；这是真实容器/服务证据，**不是模型效果实验**。

最终原始产物保存在 `work/m4-data/acceptance-final/`。单次节点故障到恢复工作区约 29.8 秒，
其中创建新 epoch 到 claim 约 4.13 秒；样本数为 1，不作性能结论。取消、TTL、节点中断
留下 3 条 UNKNOWN 脚本操作。早期镜像导入、镜像 ID 兼容失败及修复也记录在证据中。

输出目录保存：

- `frozen-plan.json`：预先冻结的测试案例、任务规格、镜像/配置和零 API 预算。
- `acceptance.json`：检查结果、版本配置、耗时、故障及证据摘要。
- `faults.json`、`capacity-samples.json`：实际故障时刻与准入采样。
- `final-report/{report.json,summary.csv,trials/*.json}`：完整状态、失败/取消、事件、账本、执行历史与 SHA256。
- `snapshot-with-incomplete/`：故意保留 sealed 任务，验证报告不会过滤未完成样本。
- `temporal-history.json`：可重放的控制历史；每个 Execution 下有 supervisor 日志、结果、恢复工作区。

`queue_seconds` 是提交到首次 claim；`elapsed_seconds` 是提交到当前 epoch 的终态事件，
不包含后续清理时长；`recovery_to_claim_seconds` 从创建恢复 epoch 到 claim，
**不是**完整故障停顿。注入故障到工作区恢复的时间另在 `faults.json` 记录。
p50/p95 附样本数，单次恢复不能作为性能基准或 SLO。UNKNOWN 记录的是脚本操作中断，
本次没有模型账单；不能推广为真实 API 计费准确性证据。

## 成本、限制与下一阶段

本阶段付费 API 调用为 0，云资源费用为 $0；使用已有本机 CPU、内存与磁盘。
4 张 lab H100 未使用。先前 $8 授权属于 M3；后续真实 pilot 最初获批 $8，第三轮前提高到累计 $20，见[模型试验](m4-model-pilot.md)。

不具备高可用，未验证宿主断电或跨机器存储。外层 Pod 是 privileged，仅适合可信开发任务。
