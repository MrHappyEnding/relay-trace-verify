# M2: Checkpoints and reliable recovery

[![中文](assets/lang-zh.svg)](m2.md) [![English](assets/lang-en.svg)](m2.en.md)

2026-10-09: M2 is accepted for **one host, trusted filesystem tasks and local Docker**.
A completed stage can resume in a fresh Execution and sandbox, keeping its Attempt
while increasing the epoch. Superseded executions cannot publish current results or
checkpoints. Two-stage native Codex recovery passed; a second agent and paired branches
remain M3 work.

## Run

Dependencies and services follow [M1](m1.en.md): Python 3.12+, Harbor 0.24.0,
temporalio 1.34.0, psycopg 3.3.6, PostgreSQL 17.6 and Temporal CLI 1.9.1 / Server 1.32.0.
Run from the repository root:

```bash
uv sync --python 3.13 --locked --group runtime --dev
uv run --no-sync python scripts/setup_temporal.py
docker compose -f infra/compose.m1.yaml up -d --wait
uv run --no-sync rtv runtime init
uv run --no-sync rtv runtime prepare
```

Start Temporal and a worker in separate terminals; reuse services already running:

```bash
work/tools/temporal server start-dev --ip 127.0.0.1 \
  --db-filename work/runtime-temporal.db --ui-disable-news-fetch
```

```bash
uv run --no-sync rtv runtime worker
```

Submit the two-stage scripted fixture from a third terminal, with **no model calls**:

```bash
uv run --no-sync rtv runtime submit --key first-m2 --staged --ttl 300 \
  --delay 15 --max-recoveries 1
uv run --no-sync rtv runtime status <trial_id>
uv run --no-sync rtv runtime history <trial_id>
uv run --no-sync rtv runtime events <trial_id>
uv run --no-sync rtv runtime ledger <trial_id>
```

Stage 1 deliberately retains an empty-input defect, verifies, stops its sandbox and
commits a checkpoint. Stage 2 restores into a fresh sandbox, fixes the defect and passes
final verification. Planned stage advance does not consume the recovery allowance.
`--max-recoveries` defaults to 0 and permits 0–3 reruns of a lost stage. For real agents,
this may add model calls: explain and confirm spending under the project agreement first.
It is not a token or monetary cap.

M2 uses `work/runtime-v2`, PostgreSQL schema `rtv2`, queue `rtv-m2-<root-hash>` and
Workflow ID `rtv2-<trial_id>`. M1 directories, `public.rtv_*` tables and Workflow histories
are retained, **not automatically migrated**. Finish active M1 tasks and stop their workers
before upgrading. Images reuse the `rtv-m1-fixture` / `rtv-m1-codex` tags; submissions resolve
them to immutable image IDs. See M1 for configuration variables such as `RTV_RUNTIME_ROOT`,
same-host path requirements and service shutdown.

## Commit and recovery contract

```mermaid
flowchart LR
    A[Stage call completes] --> B[Verify and stop entire sandbox]
    B --> P[PG: PREPARING]
    P --> U[Files and manifest / fsync / rename]
    U --> V[Independent restore validation]
    V --> C[PG: conditional COMMITTED + head + event]
    C --> N[Fresh Execution / epoch / sandbox]
    N --> R[Revalidate and restore workspace and native session]
```

- **Identity and ownership:** each stage has a physical Execution, directory and Compose
  project. PostgreSQL records the current execution/epoch. A 20-second lease renews every
  2 seconds. Phase, event, checkpoint and result writes check identity and the lease.
  Controller finalization can bypass an expired lease but must still match the current
  epoch. Lease checks use the database clock.
- **Quiescence:** the stage call returned, verification finished and the entire sandbox
  stopped. Export follows confirmation that containers are not running and have PID 0.
  The snapshot covers `/workspace` regular files, empty directories, file modes and one
  completed native session. Process memory, external services and arbitrary tool effects
  are outside its scope.
- **Manifest v2:** retains v1 file hashes and identity, adding task/image/adapter/model
  versions, stage and parent checkpoint, stop evidence, event-ID boundary, ledger revision
  and verification result. Recovery validates manifest and file hashes plus the workspace
  digest; incompatible images or tasks prevent agent invocation.
- **Conditional commit:** register PREPARING, upload local files under an immutable ID,
  then commit metadata. Only COMMITTED is restorable. An uploaded directory alone is
  insufficient. Stable operation IDs resolve lost acknowledgements. If a current execution
  committed its boundary but lost the result acknowledgement, the controller converges
  from that committed boundary.
- **Recovery:** supervisor loss or lease expiry triggers a new epoch only with a checkpoint
  and recovery allowance. Worker loss alone leaves a surviving supervisor running.
  Container/adapter errors first fail; use manual recovery below. Cancellation, exhausted
  TTL, missing checkpoints or exhausted allowance prohibit recovery.

```bash
uv run --no-sync rtv runtime recover <trial_id> --key recovery-1
```

Repeating a recovery key creates no extra execution. If the previous Temporal control run
closed, reconciliation starts a new control run for the recovered product trial. Physical
calls remain guarded by separate operation IDs. Recovery never resets TTL or usage.
`execution.recovered` records the source execution, checkpoint, discarded stage and the
window since the last committed stage; it does not claim an exact lost-token count.

## Usage and reference collection

The ledger currently tracks **one native agent stage call or one fixture command** per
operation. Admission records PENDING; observed usage becomes KNOWN, and lost/superseded
calls become UNKNOWN. Late observations can settle their original operation only, without
changing current results; conflicting known usage is rejected. Native resume adds only
incremental usage so the prefix is counted once. Internal Codex tools remain in raw
trajectories; RTV does not yet own each tool operation or deduplicate external effects.
Subscription dollar cost is `null`, UNKNOWN is not zero, and strict token/dollar admission
is unsupported.

GC protects current Trial checkpoints, Execution restore references, parent chains and
explicit references:

```bash
uv run --no-sync rtv runtime pin <checkpoint_id> --owner experiment:example
# Release implicit artifact references only when this terminal trial is no longer needed
# Metadata and history remain available
uv run --no-sync rtv runtime retire <trial_id>
uv run --no-sync rtv runtime gc --older-than 3600
# When the explicit reference is no longer needed either
uv run --no-sync rtv runtime unpin <checkpoint_id> --owner experiment:example
uv run --no-sync rtv runtime gc --older-than 3600
```

`retire` requires a terminal, cleaned trial and prevents further recovery. GC checks
references and writes tombstones transactionally before deleting files. A competing pin
and deletion cannot both win. Live uploads are protected; abandoned PREPARING and late
uploads are collectible, with retries after deletion failure. Ancestor chains can require
multiple sweeps. Tombstones and raw execution logs remain, and images are not pruned.
These are reference primitives for M3; actual experiment branching is not implemented yet.

windows, concurrent recovery, corruption, UNKNOWN/late settlement, pin/GC races and late
uploads. They are not model-performance evidence.

bill. Full trajectories and histories remain only under ignored `work/`.

## Limits and next step

Local storage uses fsync and atomic rename, but power-loss durability has not been tested;
there is no disk-loss tolerance, replication, object lock or cross-host recovery guarantee.
Epoch fencing protects authoritative PostgreSQL state and controlled artifact publication;
it cannot retract requests already sent to models or external services. Independent
workspaces contain stale file writes. The reconciler repeatedly sweeps retired Compose
identities; host failure, hard kills during sandbox creation and arbitrary late external
effects remain unverified.

Recovery operates at completed-stage boundaries, discarding in-stage file changes. Only
two trusted repository tasks are exposed, without arbitrary task uploads, HTTP API or
product UI. Repeated retired-execution scanning prioritizes correctness; scheduling scale,
index optimization and multi-node faults remain M4. This is protocol and compatibility
acceptance, not a large benchmark or evidence of improved handoff success.

See [ADR 0003](adr/0003-fenced-checkpoints.en.md) for decisions and references. M3 adds a
second agent and A-continue / B-workspace / B-summary branches from the same committed
checkpoint, with trajectory and cost comparisons.
